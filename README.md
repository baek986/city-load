## 二、 业务场景

**痛点：** 
在城市配送（如医药、生鲜、快消品）中，单仓、固定车队每天面临大量带有硬时间窗的订单。传统的调度系统往往采用「先排路线再装箱」的两段式启发式，或者将三维装箱写进巨型混合整数模型中。这导致两个严重问题：
1. **路线可行但装不下**：路线规划时只考虑容积/载重，忽略三维几何约束，导致司机到了仓库发现货装不进车厢。
2. **求解效率低下**：巨型模型在 30 店以上规模时，往往在时限内连可行解都跑不出来。

**我们的场景定位：**
单仓、固定车队。系统需要将当天订单分到车上、排出停靠顺序，并给出每件货在车厢里的三维坐标和装卸步骤。**路线和装载必须一起算：装不进车厢的路线不能当可行解。**

### 目标用户与业务价值
本系统主要面向**单仓、固定车队的城市配送调度员、物流企业运营主管以及一线装卸工人**。
- **对调度员**：系统直接输出“车辆-路线-三维装载图-装卸顺序”的一体化方案，取代过去“先排路线、到了仓库发现装不下再临时改”的割裂流程。
- **对装卸工**：3D 车厢视图（轴测/俯视/侧视）配合按站推进的装卸滑条，明确指示“后送的先靠深处、易碎品不能压、后送不挡先卸”，大幅降低装卸门槛和货损率。
- **对企业管理者**：综合成本（出车费+里程费）、时间、迟到、装卸和拆单五项指标，提供可量化的降本增效依据。在 30 店大药箱测试中，单车容量不够时自动精确拆分为多车，避免了运力浪费。

*注：当前 30 店场景下的降本效果为预期收益（基于模拟路网测算），实际企业内测效果需结合真实路网与历史订单数据进一步验证。*

## 三、 核心方案

**求解器追求的是联合意义下的最优。下界追上已经装箱的上界，间隙才标成 0。** 配了模型时，模型只并行交一版初始路线；坐标、时间窗和最优性仍由求解器决定。不配模型时，整条链路退回确定性搜索，行为与没接模型时相同。

### 核心创新

这不是「先排路线再装箱」的两段式启发式，也不是把每只箱子的位姿写进一个巨型混合整数模型。核心是：**精确的路线主问题 + 三维装箱裁判 + 二者共用同一套装卸口径**。模型若参与，只作为可被否决的初稿，不替代裁判。

#### 1. 装箱器当裁判，CP-SAT 当主审

路线主问题是自己建的异构 VRPTW（带时间窗的车辆路径问题），用 OR-Tools CP-SAT 求解，没有调用自带路径库。三维装载不进主问题的几何变量，而由确定性构造装箱器判定「这组门店、这个顺序、这辆车，装不装得下」。

装不下就加切割再解：门店子集禁止同车（集合割），停靠很少时禁止这条具体顺序（弧割）。主问题证到最优、真实装箱还有额外层数时，禁止这套精确分配（含同型车互换的所有排列），再枚举下一条次优路线，直到主问题下界追上已装箱上界。那一点才是联合最优，不是「路线最优、装箱另算」。

间隙为 0，表示在装箱器接受的摆法里，路线和装载一起达到最优。

#### 2. 装卸上界和下界说同一种层数

常见做法里，上界按每个不同的 z 毫米计一层，下界按地板面积估层数。30 店一天几百箱会把装卸项撑出虚假大间隙。

当前口径对齐了：

- **上界**：附近的 z 归入同一 50 mm 层（`z // 50`）。同店既有易碎又有非易碎时，落在地板上的易碎箱另外计数。
- **下界**：主问题里每辆车有额外层数变量，同时受地板溢出和体积 /（地板 × 最高箱高）约束，目标里与停靠次数一起计价。
- 主问题证到最优后，**不再把下界打回「不含附加层」的路线分**。层数已经写进主问题，清掉它会让间隙停在搬运项上。

装箱器仍是几何裁判。主问题只吃有效层数下界，不假装已经摆好每一箱。

#### 3. 开搜之前就切掉装不下的组合

两两同车装不下的门店直接禁止。剩余预算再扫三元组。同型车只查一辆代表车，装箱结果有缓存。已经超重或超体积的组合交给主问题的容量约束，不重复做几何。被成对切割覆盖的三元组不再查。

主问题因此更少把时间片花在「容量够、几何不够」的路线上。

#### 4. 构造阶段看货型和河岸，地理仍然优先

Clarke-Wright 和最便宜插入仍是上界的起点。合并时除了节约里程，还看两家店的货型是否互补（结实的高箱托住易碎的矮箱），以及是否在河的同一岸。地理差得远不会因为货型好就硬拼。装箱器仍然是是否可行的最终判断。

路网里河只在中间有一座桥。同岸偏好减少无必要的过桥。

#### 5. 大规模先求可行，再换更紧的子回路

子回路约束有两套。序号约束（MTZ）松弛弱、出可行解快。回路约束（`AddCircuit`）更紧，30 店上若第一轮就用，时限内可能连可行解都没有。

不超过 12 个停靠点从第一轮用回路约束。更大规模第一轮用序号约束拿到可行解和提示，第二轮再切到回路约束收紧下界。每轮带完整变量提示。加切割后沿用现有最优，不从零猜。

#### 6. 默认追分数，证明模式追间隙

默认大规模路径用短切片：第一轮约 20 秒，之后约 12 秒。上界连续两轮不改善就停，把时间花在已装箱方案上。`prove_optimal` 放宽到 40 轮、单片更长、打磨更久，切割稳定后一次吃满剩余时间，目标是让下界追上上界。

大规模默认 8 线程。同一种子分数接近，路线不保证逐停一致。`search_workers=1` 可强制单线程复现。小规模默认单线程。

#### 7. 模型初稿和确定性搜索取优

两条路同时走，只留下分数更低的那一版。分数越低越好，表示出车、耗时、迟到、装卸和拆单这些代价更小。确定性搜索照常构造、装箱并局部改进；模型在另一条时钟上，用同一份原数据交一版车辆和卸货顺序。两边都要过时间窗和装箱，再用同一个分数比较。模型更好，才换成后续 CP-SAT 的上界和提示；不好就丢掉，已经搜到的方案保持不变。

这样做的好处是：发布结果不会差于纯确定性搜索，模型只可能把起点抬高，不会把不可行或更差的路线写进结果。模型不占 CP-SAT 的时限，也没有自己的一套坐标或最优性口径，裁判仍是装箱器和分数。没配模型时这条支路不启动，求解退回确定性搜索。

模型有自己的 180 秒。它只输出车辆和卸货顺序，不写坐标，也不声称最优。时间窗或装箱没通过时，会把哪辆车、哪一段失败发回去，在这 180 秒里最多再改一轮。

密钥只放在本地 `.env`，不进仓库。调度句子（锁车、加箱、取消）仍由仓库内的解释器处理，不调用模型。

### 算法效果对比与效率提升
为了验证“精确路线主问题 + 三维装箱裁判”联合求解的优势，我们在 30 店、400 箱、窗口 8:00–20:00 的模拟场景下进行了对比测试：

| 对比维度 | 传统两段式启发式 | 巨型混合整数模型 (MIP) | 本方案 (CP-SAT + 装箱裁判) |
|---|---|---|---|
| **求解时间** | 快（秒级） | 极慢（90秒内可能无可行解） | **90 秒内给出可行解并证明 Gap=0** |
| **路线与装载一致性** | 可能路线可行但装箱失败 | 理论一致但计算爆炸 | **强一致，装不下即判定路线不可行** |
| **间隙 (Gap)** | 无下界，无法评估最优性 | 下界极弱，间隙巨大 | **上下界对齐，间隙为 0** |
| **装卸与货损** | 忽略三维几何与易碎约束 | 难以处理复杂几何约束 | **硬约束限制后送挡先卸、易碎品被压** |

**核心效率提升点**：
1. **切割前置**：开搜前直接禁止两两同车装不下的门店组合，同型车只查代表车，避免主问题把时间片花在“容量够、几何不够”的无效路线上。
2. **层数口径对齐**：上界按 `z // 50` 归入同一层，下界在主问题里设额外层数变量。解决了 30 店一天几百箱时，装卸项被撑出虚假大间隙的痛点。
3. **大模型与确定性搜索取优**：模型只输出车辆和卸货顺序，不写坐标，不声称最优，拥有独立的 180 秒时钟且不占 CP-SAT 时限。模型更好才替换，否则丢弃。这保证了发布结果不会差于纯确定性搜索。

## 四、方案目标

综合分数五项加权，先按本问题尺度归一化再相加。五项都是代价，分数越低越好。默认权重之和为 1：

| 项 | 权重 | 含义 |
|---|---|---|
| 成本 | 0.45 | 出车费 + 里程费 |
| 行驶时间 | 0.35 | 总在途时间 |
| 迟到 | 0.10 | 超过软截止时间 |
| 装卸 | 0.05 | 停靠次数 + 额外堆叠层数 + 混装时易碎品落地 |
| 拆单 | 0.05 | 同一订单拆到多辆车 |

硬约束不能用分数换：车辆载重和体积，车厢长宽高，箱子互不重叠，悬空箱子至少 75% 底面积有支撑，易碎品和不可叠放的箱子上面不能再放货，门店和仓库的硬时间窗，以及卸一家店时不用搬开后送门店的货。

软截止可以晚，只增加迟到项。早到就地等待，不记惩罚。允许拆单，但只拆整箱或整行。车辆数是上限，空车可以不出。体积一律用长、宽、高相乘。行驶时间用出发前算好的路网矩阵。只有间隙为 0 才写成已证明最优。

调用规划时可以传入别的权重。每一项先除以该问题自己的尺度：成本按最便宜的车把每个门店来回跑一趟来估，时间用同样这些来回的行驶时间，迟到按每个门店 60 分钟，装卸按门店数，拆单按订单数。

## 五、求解流程

1. 订单行拆成物理纸箱。默认一家店一个停靠点。单店装不下再拆整行或半箱。
2. 若配置了模型，此时另起线程向模型要初稿。确定性搜索不等它。
3. Clarke-Wright 与最便宜插入构造能装下的路线，再用装箱感知的插入和短时局部改进，得到确定性上界。
4. 两两、三元装载预切割写入主问题。
5. CP-SAT 在容量、时间窗、层数下界和已有切割下改进路线。模型初稿一旦通过时间窗和装箱，就在轮次之间与当前解比分数，更好才替换。
6. 构造装箱器验收。失败则加割或拆点再解，成功则更新上界。大规模轮次之间做邻域打磨，只接受装箱后分数更好的方案。
7. 主问题最优但真实层数仍高于估计时，禁止该分配并枚举下一条次优路线。

另有一个不跑 CP-SAT 的快速下界（径向/生成树行驶代价 + 车队层数下界 + 小规模时单车装箱可行性）。证明最优只用主问题自己的下界。

车厢门在车头（模型里 x = 0）。后送的门店先靠深处、贴着地板放。后送的箱子不能压在先送的上面，也不能挡在先送的货和车门之间。这是确定性构造，货量变大时搜索次数不随箱数爆炸。同一辆车、同一批货的装箱结果会缓存，模型和主线程可以同时装箱。

30 店样例使用模拟路网，不用直线距离。路口大约相距 400 米，街道沿路缓缓弯曲，街区不是方格。普通路约 29 公里/小时，每四条有一条主干道，约 50 公里/小时。一条河挡住东西向小路，北、中、南三座桥能过，河岸和桥面保持顺直。公园内部不让车穿行。6 店证明用的小例子仍是直线距离，以便和已知最优路程 13200 米对照。

##  六、应用价值

1. **真正的“路线+装载”联合最优**：打破了传统“路线最优、装箱另算”的割裂局面。通过装箱器裁判与 CP-SAT 主审的配合，确保输出的每一套路线在实际三维装箱中绝对可行，彻底消除“派了车却装不下”的尴尬。
2. **显著降低物流成本**：综合分数直接优化出车费、里程费和行驶时间（占比 80%），在 30 店大药箱场景中，单车容量不够时自动精确拆分为多车，避免运力浪费。
3. **提升装卸效率与货物安全**：将停靠次数、额外堆叠层数、易碎品落地计入代价，且硬约束严格限制“后送挡先卸”、“易碎品被压”。不仅保护了货物，还大幅缩短了司机在门店的卸货时间。
4. **求解效率与可解释性兼备**：大规模场景先求可行（MTZ），再换紧约束（AddCircuit），配合短切片和上界停滞判断，在 90 秒内即可完成 30 店、400 箱的复杂调度。大模型（LLM）仅作为可被否决的初稿提供者，不干涉核心求解，保证了系统的确定性、可复现性和极高的容错率。
5. **工程落地友好**：提供 FastAPI 接口、异步规划和重算功能，支持锁车、加箱、取消等调度句子。提供直观的 3D 车厢演示（轴测/俯视/侧视，装卸滑条），所见即所得。

## 七、演示

需要 Python 3.11+。在仓库根目录：

```bash
pip install -r requirements.txt
python -m uvicorn app.api.main:app --host 127.0.0.1 --port 8000
```

浏览器打开 http://127.0.0.1:8000/ 。首页和 `/demo` 是同一张方案页。计算不访问在线地图，图只是把已有坐标和弧画出来。演示任务存在进程内存里，重启服务后列表会清空。页面每次请求从磁盘读取，改 HTML 不用重启；改 Python 需要重启。

### 模型配置

在仓库根目录放 `.env`，模板见 `.env.example`。

三个值都有，求解才会向模型要初稿。接口需兼容 OpenAI Chat Completions，地址按服务商文档填写：

```bash
LLM_API_KEY=你的密钥
LLM_BASE_URL=https://你的服务地址
LLM_MODEL=模型名
```

`LLM_REASONING_EFFORT` 和 `LLM_THINKING` 可选。服务商支持时再填；不填则温度为 0。打开思考时，这一轮的读超时会放宽，以便等完思考再返回 JSON。

密钥、地址、模型名缺任何一项，`model_proposal` 为假。预设方案、自定义方案、`/v1/plans` 和重算都只跑确定性搜索，不发起网络请求。配齐之后，这些入口都会并行要初稿。初稿不通过或分数不更好时，发布的仍是确定性搜索的方案。规划接口的摘要里有 `model_proposal_accepted` 和 `model_proposal_note`，说明这版初稿留了还是丢了。演示页本身不展示这两项。

调度句子 `POST /v1/plans/{plan_id}/dispatch` 始终由仓库内的解释器处理，与 `.env` 是否配置无关。

## 十、工程化落地与扩展思路

### 资源需求与瓶颈分析
- **当前资源需求**：默认大规模场景使用 8 线程 CP-SAT 求解，建议部署环境至少为 8 核 16G 内存的服务器。小规模场景（≤12 停靠点）默认单线程。
- **性能瓶颈**：当门店数量超过 50 家、纸箱数量超过 1000 箱时，CP-SAT 主问题的变量规模会显著增长，求解时间可能超出 90 秒时限。
- **扩展思路**：
  1. **分单预处理**：对超大规模订单先按地理聚类进行区域切分，再并行求解。
  2. **模型降级策略**：在并发规划高峰期，可自动关闭 LLM 初稿支路（仅跑确定性搜索），以节省 API 成本并降低系统延迟。
  3. **装箱缓存复用**：同一辆车、同一批货的装箱结果已实现缓存，模型和主线程可同时装箱。未来可扩展至 Redis 分布式缓存，支持多实例部署。

### 企业落地实施路径与数据安全
- **系统对接方式**：提供标准的 FastAPI 接口。企业可通过 API 网关将本系统接入现有 TMS（运输管理系统）。订单数据通过 Kafka 或 RabbitMQ 异步推送，规划结果（路线、坐标、装卸步骤）回传至 TMS，调度员可在原有系统内查看。
- **部署维护成本**：支持 Docker 容器化部署，可一键启动。求解器与业务逻辑解耦，便于独立升级。
- **数据安全约束**：密钥只放在本地 `.env`，不进仓库。调度句子（锁车、加箱、取消）始终由仓库内的解释器处理。**对于医药等敏感行业，支持切换为本地私有化部署大模型，或对发送给外部 LLM 的订单数据进行地址脱敏处理，确保合规。**
- **关键障碍与解决思路**：企业历史数据质量（如地址不准、时间窗混乱）是最大障碍。建议前期提供数据清洗工具，并在系统中加入“硬约束冲突提示”（如：某门店时间窗与路网矩阵矛盾），辅助调度员快速修正基础数据。
